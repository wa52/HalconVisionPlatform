# 原生启动稳定性：独立复跑与故障采集

日期：2026-10-23；起点 `4c30654`。

## 结论

本轮完成了独立启动诊断能力，**没有确认或修复上轮间歇性 `0xc0000005` 的根因**。普通 HALCON 启动、带原生事件采集的启动及完整 WPF 生命周期均未复现该异常；这些成功样本不能代替故障复现或长期验收。生产算法、UI、模型、项目方案和桌面默认入口均未改动。

## 新增能力

新增不引用 HALCON 的 `tools/HalconStartupAudit`。它从进程创建开始记录自己拥有的检查子进程，覆盖 managed Main 尚未执行的故障阶段：

- 串行独立启动、逐次退出码和完整阶段检查，任何失败立即停止，无失败自动重试。
- 普通模式保留 stdout / stderr 原始字节，兼容本机 Windows OEM 中文，避免错误消息乱码丢失。
- 采集模式记录 DLL 加载路径/版本、异常线程、地址、读写类型、模块偏移及本地 minidump。未知地址仍保持未知，不据此推断 HALCON 或安装层有错误。
- 只观察自己通过 CreateProcess 创建的子进程，原生异常继续交给原进程/系统；不吞异常、不改寄存器或进程内存，不附加或结束用户窗口。
- 超时只结束自己拥有的子进程，并等待退出；记录 `CleanupConfirmed`。拒绝已有输出目录、无效次数和普通产品 exe。
- `*.dmp` 加入本仓库忽略规则。转储留在 artifacts；本次上传的证据只有审查后的 JSON / 文本，没有转储或运行期内存内容。

流程为：验证目标及全新目录 → 创建单个子进程 → 记录阶段/原生事件 → 有限等待 → 验证输出与退出 → 写入结果 → 成功才开始下一个独立样本。没有改 DLL 搜索策略、HALCON 安装、许可证、全局 WER / 注册表、内存分配器或自动重启机制。

## 采集器自身的失败与修正

最初受控 AV 自检查失败：子进程以 `0xC0000005` 退出，但只有首次机会事件，没有第二次机会，也没有转储。[红色记录](startup-20261023/collector-red.json)。这是**采集器控制场景**，不是 HALCON 原间歇故障的复现。

修正为首次 AV 也采集，同时联合最终退出码判读。已处理空引用实测也产生了首次 AV，退出码仍为 0，采集器必须识别为正常结束。连续的异常分别留存，避免先前已处理异常的转储覆盖之后致命异常的诊断。自检查直接读取 minidump 异常流，核对异常代码、地址和线程上下文，而非仅检查文件存在。

实现依照 Microsoft [调试事件继续语义](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-continuedebugevent) 和 [MiniDumpWriteDump](https://learn.microsoft.com/en-us/windows/win32/api/minidumpapiset/nf-minidumpapiset-minidumpwritedump)；异常信息结构使用 SDK 规定的 pack4。采集模式影响时序，因此与普通模式分别记录。

开发中还发现原始控制台字符解码以及读取尚未关闭的输出文件问题；已保留原字节并在关闭文件后解码，最终自检查及实际中文项目输出均通过。

## 未覆盖与下一步

没有取得原间歇故障的新原生栈，无法做“修复前失败、修复后通过”的产品级因果验证。没有验证真相机、GPU 模型长时间运行、8 小时稳定性、多显示器/DPI 或 UI 新设计；本轮没有修改界面，因此不展示旧截图充当本轮运行证据。

桌面快捷方式继续指向上一已检查的 `artifacts/desktop-preprocessing-checked/HalconVision.App.exe`。后续若独立检查再次失败，优先读取对应阶段、异常地址与本地转储，取得真实故障栈后再决定最小修复；不能用强制回退、固定 DLL、重启或成功复跑代替定位。

[收尾只读核对](startup-20261023/final-state.json)确认关键产品/接口/native DLL 哈希和桌面入口未变。本轮子进程均有退出确认，收尾进程列表没有本轮启动器或生命周期检查；系统仍有 10 月 19 日启动的旧布局进程，本轮未对它采取结束操作。未留下本轮正在运行的检查窗口或采集句柄。

本工具不是日常桌面程序的常驻崩溃采集器，仅覆盖被它创建的检查进程。若故障只在日常窗口中发生，需要另行取得该次故障的时间、检查入口或转储，不能声称本工具已经覆盖所有现场故障。
