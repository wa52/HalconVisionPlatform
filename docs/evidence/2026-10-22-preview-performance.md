# 检测预览绘制优化与颜色隔离

日期：2026-10-22；起点 `ee34b07`。本轮只修改 HalconVisionPlatform 的预览生成及检查代码，不改模型、ROI、判定阈值、HALCON 安装或授权。

## 实施范围

目标检测、分类和语义分割原先每画一个 ROI / 对象边界，都通过 `PaintRegion` 再生成整幅图像。新增内部 `OwnedPreviewImage`：首先分别物理复制 RGB 三个通道，再合成只归当前节点所有的预览；后续在这些私有矩阵上使用 `OverpaintRegion`，不为每个框复制整图。

上游矩阵、共享通道和其他节点结果禁止原位修改。构建器不暴露内部图像，直到全部绘制成功才转移给运行结果；转移后不可继续绘制或重复取走。没有转移的图像在取消、失败和关闭时释放，输出仍由 WorkflowExecutionRun 统一拥有。各节点仍输出独立 HImage 和原有叠加/数据端口，没有以未标注原图冒充 preview。

依据本机 HALCON 24.11 官方 `overpaint_region` 文档：该算子会修改已有矩阵，连带影响共享矩阵的其他对象，必须只作用于新建或物理复制图像；`copy_image` 为物理复制，`Compose3` 本身不足以保证独立性。没有使用仅复制对象引用的 CopyObj 来承诺像素独立。

## 基线与性能信号

先将旧绘制路径提取到同一生产构建器，随后调用实际构建器建立像素和性能检查。改动前 64 标注旧路径 59.474 ms、产品路径 60.526 ms，“产品耗时低于旧路径一半”断言失败、退出码 1。优化后同一检查通过。

最终同机、真实 2592×1944 RGB 原图，每组交替计时 10 次，排除前 2 次，取剩余中位数；计时不含像素哈希：

| 标注数 | 旧 PaintRegion 路径 | 优化后产品路径 |
|---|---:|---:|
| 2 | 2.629 ms | 0.911 ms |
| 64 | 62.057 ms | 2.596 ms |

这是预览绘制耗时，不含推理。64 个标注不是执行 64 次 ROI 模型推理。当前 P1–P6 每个检测节点通常只有一两个标注，因此不能把 64 标注约 96% 的绘制降幅推广为整条检测链的降幅。每个节点仍需要一个独立预览，不能宣称零复制或 GPU 显存显著下降。

## 发现并修正的旧颜色问题

最初要求所有情况与旧路径逐像素一致时，灰度用例失败。独立诊断确认：灰度 `Compose3(gray,gray,gray)` 及共享通道在旧路径中使绿色 `[50,205,50]` 实际成为 `[50,50,50]`。这不符合既定 OK 绿色 / 未检出红色 / 检出 NG 蓝色的显示要求。

新路径为每个通道单独 CopyImage，确保三个矩阵不同。灰度、共享 RGB 通道、real、uint2 都分别对绿、红、蓝、黄进行明确像素值断言，并与独立通道的 PaintRegion 参考路径对照。普通真实 RGB 则继续要求与旧路径逐像素一致。颜色修正只影响预览，不修改分类、检测或产品判定。

蓝色正确的像素断言属于绘制契约，不代表现有 P1–P6 模型已经训练或检出了专门 NG 类。

## 未解决：间歇原生启动访问异常

不能只记录成功复跑。本轮若干检查进程在启动阶段出现 `0xc0000005`，Windows 事件显示故障模块 unknown，地址 `0x0000000183eea820`。有的只留下空输出目录或测试 images 目录，没有进入本轮预览调用；托管 catch 未获得完整原生调用栈。

保留了 [事件记录](preview-20261022/native-startup-events.json)。未修改安装、许可证或尝试绕过授权，也没有用自动重启把失败视为成功。未改动的冒烟工具随后成功执行 read_image / threshold / connection / count_obj，结果 2；托管接口四份文件 SHA256 一致。

增加 `--fixture-only` 和阶段日志，单独执行 GenImageConst / PNG 保存而不创建窗口、不调用预览构建器。用上一已检查后端和当前后端各 10 次独立启动进行对照，全部 20 次通过；之后完整生命周期、布局也分别通过。这个结果说明当前不能稳定复现，但不证明异常已解决，也不足以确认根因或把它归为环境问题。

因此，本轮预览优化和有限功能回归完成，**原生启动稳定性仍是待定位问题**。不得称作全软件稳定性验收通过。为遵守检查问题处理后再正式交付的规则，桌面默认入口暂保留上一已检查版本；新候选目录仅供本轮独立验证。
